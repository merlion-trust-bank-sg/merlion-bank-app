# merlion-bank-app

Bank of Anthos (upstream `v0.6.11`, see `UPSTREAM.md`) for the Merlion Trust Bank capstone. This
repo **builds, scans and publishes** the service images to Amazon ECR in `us-east-1`. It never
deploys: Argo CD deploys from [`merlion-bank-infra`](https://github.com/merlion-trust-bank-sg/merlion-bank-infra)
(`deploy/`), and production changes there need a reviewed PR. Synthetic data only.

## From Jira ticket to production

```
merlion-bank-app                                   merlion-bank-infra
───────────────                                    ──────────────────
SCRUM-<n>-short-desc
  └─ PR ─► ci.yml: gitleaks, SCA, build + image scan (no AWS access)
       └─ 1 approval (not the author) ─► merge to main
            └─ cd.yml: build once ─► scan ─► push to ECR by digest
                       (g4-merlion-ci-build, push only)
                         └─ PR: staging digest ───────► auto-merge ─► Argo CD syncs staging
                                                         └─ smoke tests
                                                              └─ PR: same digest for prod
                                                                 1 approval ─► Argo CD syncs prod
                                                                 └─ deploy record ─► S3 Object Lock
```

1. Branch from `main` as `SCRUM-<n>-<desc>`; commit as `SCRUM-<n>: type(scope): summary`.
2. Open a PR. `ci.yml` must pass, and someone other than the author must approve.
3. Merge. `cd.yml` builds each image **once**, scans it, and pushes it to ECR tagged with the
   commit SHA. Tags are immutable, so a pushed image never changes.
4. The pipeline opens a PR in `merlion-bank-infra` that changes only the staging image digest. It
   merges automatically, and Argo CD rolls staging forward.
5. After staging passes, a PR with the **same digest** for production is opened. It needs an approval
   from someone other than its author; merging it is the production deploy.

Rollback: revert the digest change in `merlion-bank-infra`. Argo CD redeploys the previous image,
which is still in ECR.

## When a security gate fails

1. Open the failed job. It lists the package, the installed version and the fixed version.
2. **Fix first**: bump the dependency or base image and push to the same branch.
3. If there is **no fix, or the fix needs a major upgrade of upstream code** (e.g. a new major
   framework version), add an entry to `security/.trivyignore` with a comment: why it isn't reachable
   in our deployment, who proposed it, who accepted it (a reviewer other than the proposer: the PR
   approval), the Jira ticket, and an `exp:YYYY-MM-DD` expiry. After the expiry the gate fails again.
4. Never add `--exit-code 0`, `continue-on-error` or `|| true` to a scanner.

The gates fail on CRITICAL findings **that have a fix** (`--ignore-unfixed`). HIGH findings are
reported in the job output and by ECR's scan on push (per image: ECR console, or
`aws ecr describe-image-scan-findings --repository-name merlion/<image> --image-id imageTag=<sha>`),
but don't block: the application is unmodified
upstream code, so the gate is set to stop the most severe, fixable issues without turning every
upstream HIGH into a blocked release. A finding without a fix can't be acted on in a PR, so it doesn't
block either.

## Credentials

- **CI** has no AWS access at all.
- **CD** gets short-lived credentials through GitHub OIDC for `g4-merlion-ci-build`, which can only
  push images to the `merlion/*` ECR repositories. It has no access to the clusters, databases or
  Terraform state.
- No secrets are stored in this repo or in GitHub. Database passwords are generated by RDS and
  reach the pods through External Secrets (set up in `merlion-bank-infra`).

## Promotion GitHub App

`cd.yml` opens and merges the staging promotion PR in `merlion-bank-infra` as the **promotion GitHub
App** (owned by the `merlion-trust-bank-sg` org, installed on `merlion-bank-infra` only). Its
permissions: Contents and Pull requests read/write, Metadata read.

- **App ID:** Actions variable `PROMOTION_APP_ID` (not a secret).
- **Private key:** secret `PROMOTION_APP_PRIVATE_KEY` in the **`promotion`** Environment, which only
  `main` may deploy to. The key never leaves GitHub; each run exchanges it for a token valid one hour,
  scoped to `merlion-bank-infra`.
- **What it may do there:** skip the approval rule on PRs to `main` (bypass, PRs only) and write
  `promote/**` branches. It can't skip the required checks; the **staging promotion only** check
  fails any promotion PR that changes more than digests in `deploy/values-staging.yaml`.

### Rotating the private key

Every 90 days, when someone with access to it leaves, or at once if it may have leaked:

1. Org Settings -> Developer settings -> GitHub Apps -> the promotion App -> **Generate a private key**.
   A `.pem` file downloads. The old key keeps working until you delete it.
2. merlion-bank-app Settings -> Environments -> `promotion` -> update `PROMOTION_APP_PRIVATE_KEY` with
   the file's full contents.
3. Run `cd` by hand (Actions -> cd -> Run workflow) and check the promote job gets a token.
4. Back in the App settings, **delete the old key**. Delete the `.pem` file from your machine.

If it leaked: delete the old key first (promotions stop until step 2), then check merlion-bank-infra's
PRs, `promote/**` branches and audit log for anything the App did that `cd` didn't.

## CI log hygiene

GitHub stores Actions logs outside `us-east-1`. The pipelines only handle code, synthetic demo data
and scan results, never customer data or application logs. Secrets are never printed.
